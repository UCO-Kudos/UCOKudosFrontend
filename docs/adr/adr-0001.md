# ADR-0001: Monolito modular con arquitectura hexagonal

## Estado
Aceptado.

## Criterios de evaluación
- Mantenibilidad y cambio de proveedores sin tocar el negocio (EC-07).
- Facilidad de probar el negocio de forma aislada.
- Complejidad operativa acorde con el tiempo y el volumen.
- Capacidad de evolucionar hacia servicios si se requiere.

## Candidatos
- Monolito en capas tradicional (controlador → servicio → repositorio).
- **Monolito modular con arquitectura hexagonal (puertos y adaptadores).**
- Microservicios.

## Análisis
| Candidato | Cumple | Razón |
|---|---|---|
| Capas tradicional | Parcial | Simple, pero el negocio queda acoplado a la tecnología (JPA, SDK de proveedores). |
| **Hexagonal modular** | **Sí** | El dominio no depende de infraestructura; los proveedores son adaptadores intercambiables. |
| Microservicios | No (por ahora) | Complejidad operativa, red y consistencia desproporcionadas para el alcance y el tiempo. |

**FODA de la opción elegida.** *Fortalezas:* pruebas aisladas, bajo acoplamiento, sustentable con el vocabulario del curso. *Debilidades:* más clases (puertos y adaptadores). *Oportunidades:* separar módulos en servicios si crece la carga. *Amenazas:* sobreingeniería si no se cuida la simplicidad.

## Recomendación
**Monolito modular hexagonal**, con la regla de dependencia `infraestructura → servicios → dominio` verificada con ArchUnit (reglas AR-01..AR-08, ver 04).

## Consecuencias
- Cada capacidad externa se define primero como **puerto**.
- Los adaptadores son el único lugar con código de proveedor.
- Un solo artefacto de despliegue, sin estado, escalable horizontalmente.
